# U_MERRICK — ICONIC FITS Gift Card Management

Django application for U_MERRICK's free loyalty rewards: ₦10,000 and ₦15,000 fixed discounts, and 10% purchase discounts. Cards are generated by Admin, activated by Staff at handoff, then become redeemable after 72 hours and expire 60 days after activation. The expiry boundary is exclusive: redemption is rejected when server time is greater than or equal to `expires_at`.

## What is included

- Django templates for Admin/Staff, role-checked endpoints, staff accounts and password changes.
- Cryptographic card-code generation, UUID-backed QR links, individual/batch print-to-PDF previews, camera QR scanning and manual code lookup.
- Atomic activation and redemption services. MySQL InnoDB row locks and a database one-to-one constraint enforce single-use redemption; SQLite is used for local development.
- Decimal-based discount arithmetic, append-only application audit events, CSV card report, Django admin read-only audit view, and django-axes login throttling.
- Staff can record a customer phone number and amount spent when activating a card. Both fields may be left blank. The phone input has a fixed `+234` prefix and accepts exactly 10 digits after it; for example, `07012345678` is stored as `+2347012345678`. Redemption already records the full purchase amount, discount, and payable balance. Each successful activation and redemption audit row shows its recorded purchase amount, and the CSV report includes both amounts. Earlier cards without activation spending remain blank rather than being treated as zero.
- User-provided card reference and logo in `static/brand/`.
- A separate item price list: Admin adds one or several items at once, searches the compact list, and taps an item to open its change-price/name and inactive/restore options. Names are saved in title case. Staff can search and view active item names and prices. Each item displays when its price was last changed.

## Price list on staff phones

Open **Price list** inside the installed app while online at least once. The installed app has its own saved data on iPhone, so opening the list only in Safari does not prepare the installed app for offline use. The staff page saves the active item names, prices, and last price-update times on that phone. The installed app opens the saved price list when launched offline, including after sign-out. A last-synced timestamp shows how old the saved copy is. The page refreshes when it comes online, when brought to the foreground, and periodically while open. Inactive items disappear from Staff's list after the next successful sync; Admin can still see and restore them. Offline prices can be outdated until the phone reconnects. Clearing the app's site data removes the offline copy. Offline access is intended for staff's private phones and does not authorize gift-card actions.

The authenticated app header includes **Refresh** to check for a PWA update and reload the current page. When the installed app opens with an active session, a U_MERRICK welcome screen offers **Continue** or **Sign out**. Normal browser tabs continue directly to the page; unauthenticated users still see the login page. The welcome screen returns when the installed app has been in the background for at least five minutes.

## Local setup (Windows PowerShell)

Reuse the existing .dx environment. Development uses the explicit
umerrick.settings.development settings module and SQLite by default:

```powershell
.\.dx\Scripts\Activate.ps1
Copy-Item .env.development.example .env
python -m pip install -r requirements.txt
python manage.py migrate
python manage.py createsuperuser
python manage.py runserver
```

Open `http://127.0.0.1:8000/`. The first superuser is the Admin. Admins create Staff accounts at **Staff**; the initial password is shown to the Admin once and Staff must change it at first login. Staff use **Scanner** to activate or redeem cards. Generated cards can be previewed and printed or saved as PDF from the browser print dialog.

Sign-in warns users to contact an administrator after five failed attempts. Ten failed attempts for the same username and IP cause a five-minute lockout with a visible countdown; an administrator can reset a forgotten password from Staff accounts. After login, a saved destination outside a staff member's permissions opens their dashboard instead. Direct GET navigation to a restricted page also returns to the dashboard; protected API and form actions still reject unauthorized requests.

The Admin selects each new staff member's access to activation, redemption, and the price list on the Staff page and can change it later. Existing staff keep all three permissions when the migration is applied. The Overview's team performance table includes staff and admins and uses all-time figures: a redeemed card is credited to the person who activated it, regardless of who redeemed it. Run migrations after deploying this change. A device that is offline cannot learn about a newly revoked price-list permission until it reconnects; the app clears its saved price list on the next authenticated online page load.

## Environment and deployment separation

The local .env file is Git-ignored and should be created from
.env.development.example. Development uses db.sqlite3 when DATABASE_URL is
unset. The production server must use
DJANGO_SETTINGS_MODULE=umerrick.settings.production, a new random
DJANGO_SECRET_KEY, exact allowed hosts and CSRF origins, and a MySQL
DATABASE_URL. Production settings do not load the local .env file and refuse
missing secrets, wildcard hosts, non-HTTPS CSRF origins, or a non-MySQL
database. URL-encode special characters in database credentials. Never commit
.env. See DEPLOYMENT.md for the complete local → GitHub → production workflow.

## Production deployment

1. Install dependencies in a supported Python environment and provide MySQL with InnoDB tables, `utf8mb4`, and the `mysqlclient` driver from `requirements.txt`.
2. Set the environment variables; use a dedicated least-privilege database user and a private, TLS-protected database connection. Django configures MySQL sessions for read-committed isolation. Grant the migration user permission to create the append-only audit triggers; use a more restricted database account for routine application traffic where practical.
3. Run `python manage.py migrate` and `python manage.py collectstatic --noinput` as a deployment step.
4. Serve `umerrick.wsgi:application` with Gunicorn behind a TLS-terminating reverse proxy. Set `DJANGO_ALLOWED_HOSTS`, preserve `X-Forwarded-Proto: https`, and enable HTTPS. Production mode enforces HTTPS redirects, secure cookies, HSTS, `nosniff`, and frame denial. Camera scanning requires HTTPS (localhost is allowed by browsers for development).
5. Create the initial Admin with `python manage.py createsuperuser`; do not use default credentials. Back up MySQL and uploaded media separately.

## Backup and recovery

Back up the production database with `mysqldump --single-transaction --routines --triggers umerrick > umerrick.sql`, using a MySQL option file for credentials rather than putting a password in the command. Restore to an empty database with `mysql umerrick < umerrick.sql`, then deploy the matching application release and run migrations. Include the audit triggers in backups, keep encrypted off-site copies, and periodically verify a restore. SQLite local data is `db.sqlite3`; stop the development server before copying it.

## Tests

Run `python manage.py test giftcards`. Tests cover generation, unique codes, QR/manual lookup, authorization, activation, the 72-hour and expiry boundaries, single-use redemption, discounts, account security, and audit events. SQLite tests verify the database uniqueness constraint; use MySQL InnoDB in staging to exercise row-lock behavior under concurrent requests and confirm the audit triggers reject updates and deletes.
